- `internal/throttle` adds the upload-rate dimension HARDENING-PLAN §16 says is missing ("§5 has no bandwidth dimension at all"): a hand-rolled, zero-dependency token bucket (`io.Writer`/`io.Reader` wrappers, context-aware, cancellable, concurrency-safe, no busy-wait, asserted against a fake clock rather than wall-clock sleeps) plus an estimator that derives a ceiling from measurement. `config.ResourcePolicy` gains `uploadMode` (`auto` default, `manual`, `unlimited`), a manual limit and the derived measured rate, through the same strict decoder as before; old three-field payloads still decode and inherit `auto`. Measurement is HYBRID by founder decision: ONE active speed test at setup, then PASSIVE samples from transfers that were happening anyway, because a periodic active test burns the metered data cap §16 warns about. The statistic is a trimmed 25th percentile (not a mean — a mean hides the slow observations that are what saturation feels like) with a 0.7 headroom factor derived from SQM/bufferbloat shaping practice, and saturation is detected from RTT rising above the windowed minimum (BBR-style baseline) with multiplicative backoff and slow recovery. Failure, implausible measurements and stale samples all fall back to a conservative default derived from §16's slowest documented uplink — never to unlimited.
- HONESTY, and it is the important line here: NOTHING large is throttled today. There is no bulk data upload path in the connector — `internal/bundletransfer` moves 6 KB enrollment bundles, and the Time Machine / JuiceFS path that would saturate a home uplink for hours is gated behind §21 Step 0 (an untested 200 GB backup and timed restore). `status.uploadThrottle.enforced` is hardcoded false. Metered detection is also absent: the interface, the policy and the 64 KiB/s keep-going ceiling are in Go, but the only reliable macOS signal is NWPathMonitor's `isExpensive`/`isConstrained`, which is Swift and cannot be built or tested in this sandbox, so metered status reports `unknown` and no ceiling is guessed. The §16 per-donor MONTHLY bandwidth budget and cap-aware scheduling are not implemented, and a bytes/second ceiling is not a substitute for one.
- `internal/contribution` implements HARDENING-PLAN §36.4's conditional-contribution rule ("default-on must be **conditional**, never unconditional: pause when **on battery**, when **thermally throttled**, when the user is actively working, or when disk is low … visible in the connector UI per §26, so a user can always see why their Mac is or is not contributing"). Three dimensions were missing and are now built — power source, thermal pressure, and free disk on the volume Nexal stores data in; the fourth, "the user is actively working", already existed in `agent.Telemetry` (ioreg `HIDIdleTime` against the owner-set `idleSeconds`) and is FORWARDED, not reimplemented. It follows `internal/throttle`'s convention for an unavailable platform signal exactly: a first-class `Unknown` that is never guessed in either direction, an injectable `Source`, and a visible reason string per condition. The macOS probe is behind `//go:build darwin`, reuses the existing `agent.diagnostic` helper (2 s context, `WaitDelay`, 256 KiB bounded buffer, fixed sanitized env, absolute paths, no shell), and every policy decision is tested on Linux against captured output. Zero new dependencies: `syscall.Statfs` directly, no `x/sys`.
- THE TWO PAUSES ARE SEPARATE, and this is the part most likely to be broken by a later change. `config.Paused` / `SetPaused` is the owner's deliberate, PERSISTED choice. Condition-based withholding is AUTOMATIC, TRANSIENT and memory-only; it is never written into that flag, because doing so would clear an owner's own pause the moment the machine cooled and would make a machine-made pause indistinguishable from a deliberate one. `TestAutomaticWithholdingNeverTouchesOwnerPause` and `TestEachPauseSurvivesTheOther` assert both directions, including that the owner's pause survives a cool-down on disk and that an owner's resume does not clear a live thermal condition.
- UNKNOWN NEVER PAUSES, deliberately, and it is commented as such in code: an unreadable probe that withheld would silently switch off every host in the fleet and the fleet would look idle rather than broken. A missing probe, a failed command, stale observations (> 90 s) and unparseable output all report unknown with a visible reason and keep the host contributing.
- THERMAL IS POSITIVE-ONLY AND CURRENTLY INERT ON APPLE SILICON, and this is the honest headline. Real output from the founder's Apple silicon laptop, captured while it was cool, idle and on AC, is `Note: No thermal warning level has been recorded` / `No performance warning level has been recorded` / `No CPU power status has been recorded`. Because that machine was genuinely healthy, silence is the CORRECT output for a working probe — which makes it indistinguishable from a Mac that never reports thermal data at all. "Not throttled" therefore cannot be concluded from silence at any price. `ThermalFromTherm` believes a stated `CPU_Speed_Limit` below 100 or a nonzero thermal/performance warning level and returns UNKNOWN for everything else, including `CPU_Speed_Limit = 100`. Consequence, stated rather than hidden: on the founder's M2 and M4 hardware the thermal condition will read `unknown` and will not withhold, so §36.4's thermal clause is NOT yet enforced on that hardware. The authoritative source is Swift's `ProcessInfo.processInfo.thermalState` (`.nominal`/`.fair`/`.serious`/`.critical`); `powermetrics(8)` is rejected because it requires root and a user-level agent must not need sudo.

- THRESHOLDS, and where they come from. Disk floor default **10 GiB**, owner-tunable 1 GiB–1 TiB via the new optional `minFreeDiskBytes` in `config.ResourcePolicy` (same strict exactly-once decoder, and old three-field payloads still decode): it is anchored on the founder's standing **5 GB free-drive decision (§39.6)**, since one free-tier Nexal Drive can legitimately land 5 GB of someone else's data on a host, plus an equal margin for macOS's own swap/snapshot/update needs — the disk analogue of the existing `ReserveMemoryBytes` reserve. Probe cadence is 15 s (not the 2 s telemetry tick) because power and thermal are not two-second events and spawning two processes every two seconds to check whether we are on battery would itself cost measurable battery.

- `internal/stun` adds a hand-rolled, ZERO-DEPENDENCY RFC 5389 binding client, and `TRANSPORT-NAT-DESIGN.md` (repo root) records the transport decision. THE KEY FINDING is that cross-VLAN peer transport was ALREADY PERMITTED: `pool.privateIP` (`peer.go:314-317`) accepts any RFC1918 address regardless of subnet, so `10.20.0.5` on VLAN 20 is as acceptable as `192.168.1.5` on VLAN 1. What does not cross a VLAN is DISCOVERY — mDNS joins `224.0.0.251`/`ff02::fb` (`discovery/mdns.go:40-41`), link-local multicast that routers do not forward. Cross-VLAN therefore needed a way to SUPPLY an address, not a relaxation of the security rule, which made the change far smaller than it looked. `privateIP` is untouched and a public endpoint is still refused everywhere.
- STUN IS OBSERVABILITY, NOT CONNECTIVITY, and this is the honest headline. STUN ALONE ESTABLISHES NO CONNECTION: a reflexive address is useless without (a) a coordinator signalling it to the other peer and (b) both peers dialling simultaneously to punch the hole, and NEITHER EXISTS. `nexal doctor --stun` answers "am I publicly dialable, what NAT class am I behind, would hole punching even be worth implementing here" and nothing more. Classification is a TRI-STATE with UNKNOWN first-class: two distinct servers are queried FROM ONE LOCAL SOCKET (mappings are keyed on the local port, so two sockets would report "symmetric" on every NAT on earth), same reflexive address from both means endpoint-independent, different means endpoint-dependent/symmetric, and fewer than two answers means unknown. A test asserts no summary string ever claims hole punching "will work".
- STUN security properties, each a deliberate refusal: 96-bit `crypto/rand` transaction id verified BEFORE any attribute is trusted (an unmatched reply is counted as a possible off-path spoof and discarded, never parsed for an address); `ALTERNATE-SERVER` and every redirect IGNORED rather than followed; reads bounded to 1280 bytes; every attribute walk bounds-checked against the declared length; every exchange context-bounded with a socket deadline. `XOR-MAPPED-ADDRESS` (0x0020) for IPv4 and IPv6, legacy `MAPPED-ADDRESS` (0x0001) accepted as a fallback and reported as legacy, XOR form winning when both appear. Defaults `stun.cloudflare.com:3478` and `turn.cloudflare.com:3478`, configurable. EVERY TEST RUNS OFFLINE: the transport is an injectable interface, malformed/truncated/wrong-transaction-id/unknown-attribute packets are table-driven fixtures, and the one socket any test opens is an in-process loopback UDP responder. No test contacts a real STUN server.
- CLOUDFLARE TURN IS REJECTED, recorded with reasoning in `TRANSPORT-NAT-DESIGN.md` §3. It is a relay, not a direct path: Cloudflare throttles a client above 50–100 Mbps and 5–10 kpps, which is the opposite of the bulk-backup goal; it costs $0.05/GB after a 1000 GB/month free tier shared with the SFU, so one 200 GB Time Machine restore is a fifth of the free tier; and decisively it puts the bandwidth bill on the company balance sheet, which HARDENING-PLAN §16 line 899 exists to prevent ("Running relays yourself puts the bandwidth bill back on your balance sheet, which is the thing this section exists to avoid") — the same ground on which the plan already rejected Tailscale ("its DERP relays are someone else's infrastructure"). §16 also warns that relaying bulk third-party bytes through Cloudflare risks account action rather than an overage line. Also recorded: a three-way `cloudflared` tunnel is NOT possible, because `cloudflared` is outbound-only to the edge and two instances cannot peer. Cloudflare STUN is accepted precisely because it relays nothing and costs nothing.
- CONFLICT RAISED AND DELIBERATELY NOT RESOLVED (`TRANSPORT-NAT-DESIGN.md` §6): HARDENING-PLAN §16 line 872 selects go-libp2p for the data plane (AutoNAT + DCUtR + Circuit Relay v2), which conflicts with the founder's standing hand-roll/zero-dependency rule for the connector. The tradeoff is stated both ways — hand-rolled ICE/DCUtR is a serious, timing-bug-prone undertaking whose failures only appear on real customer networks, while libp2p is proven and identity-compatible but an enormous transitive dependency in a binary whose review posture is "we read every line that ships". - QR ENCODING IS HAND-ROLLED IN `internal/qr` WITH ZERO NEW DEPENDENCIES: byte mode, error correction level M, lowest fitting version, Reed–Solomon over GF(256), interleaved blocks, matrix placement, format and version information, all eight mask patterns scored by the four penalty rules. HOW IT WAS PROVED, precisely, because "it looks like a QR code" is not evidence: (a) EXTERNAL KNOWN-ANSWER VECTORS from the ISO/IEC 18004 tables and the published thonky.com tutorial — the eight level-M format strings, the version strings for 7–14, a 1-M Reed–Solomon codeword vector, and the full 5-Q four-block data/ECC/interleaved final message; (b) GOLDEN MATRICES from python `qrcode` 8.2, an INDEPENDENT encoder, committed as `internal/qr/testdata/golden-masks.txt` (four payloads × all eight forced masks) and compared module for module; (c) a wider cross-check run outside the test suite — 28 payloads from 1 to 2331 bytes spanning versions 1–40 × 8 forced masks = 224 symbols, zero module differences and identical penalty scores, with provenance recorded in `internal/qr/testdata/README.md`; (d) a TEST-PACKAGE DECODER that reads the symbol back through format information, de-interleaving, syndrome checks and byte-segment parsing, round-tripping every version and asserting the padding tail rather than ignoring it; (e) OpenCV 5.0's `QRCodeDetector`, a third implementation and a real scanner rather than an encoder, decoded 10 of 13 ASCII payloads byte-identically, including the 291-byte version-13 pairing payload — the 3 failures reproduce when OpenCV is fed python `qrcode`'s OWN matrix for the same payload, so they are detector limits on large symbols, not encoder faults. The cross-check EARNED ITS KEEP: it found a real bug, the two format-information copies were mirrored, which every self-consistent round-trip had happily accepted.
